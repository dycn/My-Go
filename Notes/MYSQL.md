#### 分库分表
- 原因
    - 数据量大查询慢 或者 因为单体结构因为某些问题会影响整体数据停机优化 或者 io瓶颈
- 方法
    - 垂直 （解耦）
        - 单体架构服务拆分微服务（防止可扩展性差）
    - 水平 （性能）
        - 数据量大 （非页节点方磁盘，索引放内存 放不下）
        - 连接数不够用

    - 分库
        - 垂直分库 某些表单独拿到库中
        - 水平分库 
    - 分表
        - 垂直分表 字段单独拆分出来
        - 水平分表 表里数据多 将不同数据分到不同表
- 问题
    - 垂直分库
    - 垂直分表 
    - 水平分库
    - 水平分表
    - 技术
        - 跨库跨表联查 (企业里一般做法是 定期抽数据加入镜像表或者影子表) 跨表可以用宽表 把多个表数据聚合到一张表
        - 分布式id 主键自增id (可以设置两个表起始id不一样 或者 使用雪花算法生成唯一id)
        - 分布式事务 每个数据库回滚用自己的undolog  引入中间件(SEATA)解决
    - 业务
        - 数据怎么分 
            - 取模 查询最频繁的字段 hash  其他字段可能就全表查询 所以加二级索引（ES 倒排索引）
            - 时间分块
        - 扩容 不停机扩容
            - 双写
            - 异步同步
    - 主从复制
        - 监听主节点写操作 记录binlog中 从节点拉到中继日志然后同步数据  (中继日志保证写入顺序，速度快，是主从之间的缓冲 主不必等从写入就可以之间发送下一个操作)



#### 索引命中
- 索引类型
    - 主键索引 特殊的唯一索引
    - 唯一索引 允许为空 如果是组合索引，组合必须唯一
    - 普通索引
    - 组合索引 一个索引包含多个列，多用于避免回表查询
    - 全文索引
- 设计原则
    - 适合索引的列 出现在where select的子句
    - 基数（整个集合中不同的个数）较小的类 索引效果小 比如性别
    - 短索引 如果长字段列建立索引，建议使用前缀索引，前缀的位数，可以从区分度和节约索引空间考量
    - 不可过度索引 结合业务量适量使用。索引需要额外硬盘空间，查询时会加载到内存中，修改表时会修改甚至重构索引，索引列越多，时间越长
- 回表操作
    - 在索引命中后，mysql可能需要执行回表操作来获取其他列的值，可能会增加一些额外的开销
    - 覆盖索引 查询所需的所有字段都包含在索引中，无需回表
    - 优化回表
        - 使用覆盖索引
        - 根据实际查询需求 设计使用合适的索引
        - 使用合适的查询字段 避免查询表中所有字段
- 优化
    - 如果使用索引比全表扫描还慢，则不会使用索引。返回数据比例超过30%
    - 前导模糊查询不能命中 where name like '%杰'
    - 数据类型隐式转换时候不会命中索引 where name=1 （name是varchar）
    - 复合索引下，查询条件不包含索引左边部分
    - union、in、or都能命中索引，建议用in。查询cpu消耗 or>in>union
    - 用or分隔开的条件，如果or前的条件有索引，而后面的没有索引，那么涉及到的索引都不会引用
    - 负向条件查询不能使用索引，可以优化为in查询。 （xxx not in()）
    - 范围条件查询可以命中索引。 < <= > >= between
    - where后字段执行计算（函数），不会命中索引
    - 利用覆盖索引进行查询，避免回表
    - 建立索引的列，不允许为null
    - 更新频繁的字段不适合建立索引 因为b+树会重构索引
    - 区分度不大的字段不适合建立索引
    - 多表关联时，保证关联字段上一定有索引
- 多个索引
    - 存在多个索引，优化器一般通过比较扫描行数、是否需要临时表以及是否排序，来作为选择索引的判断依据

- 如何查询问题

    - 服务拆分

    - 数据库分库分表
    - 缓存

    - 计算机横向扩展
    - 服务优化 拆分 负载均衡 容灾扩展
    - 监控 性能指标采集
    - 数据库
